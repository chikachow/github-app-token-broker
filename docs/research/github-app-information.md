# GitHub App information RPC findings

Research-only findings for a read-only, internal Cloudflare RPC surface authenticated to GitHub with one App JWT. Verified 2026-08-15 against the official GitHub and Cloudflare documentation.

## Recommended v1 surface

GitHub documents the following endpoints as App-authenticated endpoints requiring a JWT. Their successful response bodies should be returned with GitHub's field names and nesting; the RPC should not add an envelope or substitute repository/installation concepts.

| RPC method                         | GitHub endpoint                                                                                                                               | Inputs                                                                                                                | Successful response                                                                                                                                       |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getApp()`                         | [`GET /app`](https://docs.github.com/en/rest/apps/apps#get-the-authenticated-app)                                                             | None                                                                                                                  | The authenticated app object, including the documented app metadata and `installations_count` when present.                                               |
| `listInstallations(input)`         | [`GET /app/installations`](https://docs.github.com/en/rest/apps/apps#list-installations-for-the-authenticated-app)                            | `page`, `per_page` (maximum 100), `since`, and `outdated`; GitHub documents defaults of page `1` and `per_page` `30`. | The upstream array of installation objects.                                                                                                               |
| `getInstallation(input)`           | [`GET /app/installations/{installation_id}`](https://docs.github.com/en/rest/apps/apps#get-an-installation-for-the-authenticated-app)         | `installation_id`                                                                                                     | The upstream installation object; GitHub documents `200` and `404` outcomes.                                                                              |
| `getRepositoryInstallation(input)` | [`GET /repos/{owner}/{repo}/installation`](https://docs.github.com/en/rest/apps/apps#get-a-repository-installation-for-the-authenticated-app) | `owner`, `repo`                                                                                                       | The upstream installation object; `owner` and `repo` are case-insensitive, and `repo` excludes `.git`. GitHub documents `200`, `301`, and `404` outcomes. |

The corresponding input names should remain GitHub-shaped (`installation_id`, `per_page`, and so on), while URL construction and validation remain inside the implementation. The endpoint documentation is the authority for the accepted path and query parameters and response bodies. ([GitHub App endpoints](https://docs.github.com/en/rest/apps/apps))

## Explicitly out of v1

[`GET /installation/repositories`](https://docs.github.com/en/rest/apps/installations#list-repositories-accessible-to-the-app-installation) lists repositories accessible to an installation, but GitHub documents a GitHub App **installation access token** as its supported fine-grained token type. GitHub allows an unauthenticated exception only when requesting public resources; that does not expose the installation's app-visible repository set. It therefore requires an installation access token for the intended installation-repository use case and is excluded from this App-JWT-only v1 surface.

## Cloudflare RPC constraints

- A service binding calls another Worker without a publicly accessible URL and is intended for internal APIs. A Worker exposes RPC methods by extending `WorkerEntrypoint` and adding public methods. Named `WorkerEntrypoint` classes can be exported and selected by a service binding, so a single `GitHubAppInformationEntrypoint` is a suitable capability boundary. ([Service bindings RPC](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/))
- Only explicitly exposed RPC objects/functions are callable; private class properties and arrow-function instance fields are not exposed. RPC methods should therefore be ordinary prototype methods, and App credentials should remain private. ([RPC visibility and security](https://developers.cloudflare.com/workers/runtime-apis/rpc/visibility/))
- `wrangler types` generates `Service<WorkerEntrypoint>` client types and async client stubs for the binding. The caller should treat every method as asynchronous. ([RPC TypeScript](https://developers.cloudflare.com/workers/runtime-apis/rpc/typescript/))
- `fetch()` retains Fetch API semantics rather than RPC method semantics; `connect()`, `dup`, and `constructor` are reserved or disallowed names. The proposed method names avoid those names. ([RPC reserved methods](https://developers.cloudflare.com/workers/runtime-apis/rpc/reserved-methods/))
- Exceptions cross the RPC boundary with standard `name` and `message`, but not their own properties such as `status`, `cause`, or other custom fields. Any error contract that needs structured upstream status data must use a plain data result or encode that data in the stable error contract rather than relying on custom exception properties. ([RPC error handling](https://developers.cloudflare.com/workers/runtime-apis/rpc/error-handling/))

## Boundary recommendation

Use one named, service-bound `GitHubAppInformationEntrypoint` exposing only the four v1 methods above. Keep the interface read-only, use the configured App JWT internally, preserve GitHub's successful JSON shapes, pass through GitHub's pagination inputs without auto-pagination, and add repository enumeration only in a later version that explicitly introduces installation-token handling. This is a design recommendation derived from the endpoint authentication requirements and Cloudflare's named-entrypoint/capability model. ([GitHub App endpoints](https://docs.github.com/en/rest/apps/apps), [Cloudflare service-binding RPC](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/))
